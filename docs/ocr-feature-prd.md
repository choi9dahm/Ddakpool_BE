## Product Requirements Document: 이미지형 채용공고 OCR 파싱

**Author**: Harriet Choi
**Date**: 2026-08-23
**Status**: Draft
**Stakeholders**: TBD
**관련 문서**: [`ocr-feature-spec.md`](./ocr-feature-spec.md) — 본 PRD와 함께 작성된 엔지니어링 설계 별첨(CLOVA OCR 기반). 상세 구현 내용은 부록(9절) 및 본문 인용 참고.

### 1. Executive Summary

사람인/잡코리아 공고 중 상세요강을 이미지(스크린샷)로만 제공하는 "이미지형 공고"는 현재 딱풀에서 핵심 필드(자격요건/우대사항/담당업무 등)가 전부 빈 채로 저장되고, 역량키워드도 추출되지 않는다. OCR로 이미지 속 텍스트를 추출해 기존 LLM 필드·키워드 추출 파이프라인에 그대로 흘려보내, 이미지형 공고에서도 자동 채움이 동작하게 한다. 대상은 이미지형 공고를 저장하는 모든 딱풀 사용자이며, URL 파싱만으로 자동 적용되기 때문에 사용자가 별도로 학습할 UX는 없다.

### 2. Background & Context

- **현재 동작**: 파서가 `is_image_based = true`로 판정하면 카드는 저장하되(spec 2-3, "파싱이 실패해도 저장 자체는 막지 않는다" 원칙) `job_description`/`qualifications`/`preferences` 등 핵심 필드를 비워둔다. `qualifications`/`preferences`가 비어 있으면 역량키워드 LLM 추출 자체를 건너뛴다(`Ddakpool_BE/src/services/jobService.ts:260`). 저장 직후 `[POP-11]` 팝업으로 "이미지형 공고는 내용 인식이 정확하지 않을 수 있어요. 입력된 내용을 검토해 주세요."라는 경고만 노출한다.
- **실제로는 "부정확"이 아니라 "시도조차 안 함"**: 이 간극이 이번 기능의 핵심 문제다.
- **계측 공백**: 리포지토리 전체에서 서버측 PostHog 캡처는 `signup_completed` 1건뿐이며(`grep capturePostHog`), 파싱 결과나 `is_image_based`를 기록하는 이벤트가 없다. 즉 이미지형 공고가 전체 저장량 중 몇 %인지, 실측 데이터가 현재 존재하지 않는다 — 이는 Open Questions에서 별도로 다룬다.
- **UT 근거 — 정성 데이터로는 이미 반복 확인된 문제**: 계측 로그는 없지만, 사용성 테스트(UT) 2회에서 이미지형 공고 파싱 실패가 반복 관찰됐다.
  - [1차 UT 정량 분석](https://app.notion.com/p/harriet-choi/1-UT-846d018cdac08292a28a81aca6a0a22c) (2026-07-13~14, n=6): 강\*진 1명이 "이미지형 공고 반복 저장 → 정보 누락"을 겪음(파싱 오류 사례 중 1건).
  - [2차 UT 정량 분석](https://app.notion.com/p/harriet-choi/2-UT-f49d018cdac083819a98010ca2bcfce4) (2026-07-24, n=5): **5명 중 3명(60%)**이 동일 문제를 재현 — 한\*주(핵심 정보 인식 실패), 장\*(우대사항 빈칸), 이\*나(담당업무에 본문 전체가 통째로 삽입). 보고서 §6에서 "이미지형 공고 파싱 실패"를 발견 빈도 3위이자 **"최대 이탈 요인"**으로 명시적으로 태깅했다. 특히 한\*주는 저장한 공고가 전부 이미지형이라 핵심 필드 인식에 계속 실패하자 "이럴 거면 그냥 사람인·잡코리아에서 보는 게 더 빠르지 않나"라고 발언 — 서비스를 쓰는 이유 자체에 의문을 제기한 유일한 사례다. 이미지 첨부 기능 자체는 있으나 "첨부해도 요약·역량 추출이 안 됨"을 확인하고 실효성에 의문을 표한 점도 함께 기록됨.
  - 즉 발생 빈도가 1차 대비 2차에서 늘었고(1/6 → 3/5), 재발이 아니라 **반복·악화되는 핵심 결함**으로 확인된 상태 — 계측 공백과 별개로 이 PRD를 P0로 착수할 근거는 UT로 이미 충분하다.
- **선행 리서치**: 시장 조사·경쟁사 벤치마크는 진행하지 않음(N/A). 본 PRD는 내부 코드/스펙 분석 및 위 UT 데이터에 기반한 1차 초안이다.

### 3. Objectives & Success Metrics

**Goals**:
1. 이미지형 공고 저장 시 사용자 조작 없이 자격요건/우대사항 등 핵심 필드가 자동으로 채워지게 한다.
2. 이미지형 공고도 역량키워드 추출·필터링 파이프라인에 정상 편입시킨다.
3. OCR이 실패하거나 지연되어도 기존 저장 원칙("파싱 실패해도 저장은 막지 않는다")을 깨지 않는다.

**Non-Goals**:
1. 다국어 OCR — 현재 딱풀이 다루는 공고는 전량 국문이므로 이번 단계에서 불필요.
2. 이미지 전처리(이진화, 회전 보정 등)를 통한 정확도 튜닝 — 실측 정확도가 목표에 못 미칠 때 다음 단계에서 착수.
3. OCR 결과 캐싱 — 동일 `source_url` 재파싱은 이미 `409 duplicate_url`로 막혀 있어 캐싱 이득이 없음.
4. `[POP-11]` 팝업 카피/UX 개편 — 기존 경고 문구는 OCR 도입 후에도 여전히 유효(실제 인식을 시도하고 부정확할 수 있다는 의미로 자연스럽게 부합)하므로, 실측 정확도 확인 전까지 변경하지 않는다.

**Success Metrics**:

| Metric | Current | Target | Measurement |
|---|---|---|---|
| 이미지형 공고 중 `qualifications`/`preferences` 중 1개 이상 채워지는 비율 | 0% (코드상 확정 — 현재 이미지형 공고는 필드 추출 자체를 시도하지 않음) | 60% 이상 | 신규 계측 이벤트 (5절 P0-3) |
| 이미지형 공고 카드에 역량키워드 1개 이상 노출되는 비율 | 0% (`jobService.ts:260` 키워드 게이트에 막혀 도달 불가) | 위 필드 채움 비율에 연동해 상승 | 동일 |
| `POST /jobs/parse` 응답시간 P95 (이미지형 공고 한정) | 미측정(현재 즉시 빈 값 반환) | 기존 대비 +8초 이내 (`OCR_TIMEOUT_MS` 예산과 일치) | 서버 로그/APM |

### 4. Target Users & Segments

전체 딱풀 사용자 중 사람인/잡코리아에서 이미지형 공고(상세요강이 스크린샷으로만 제공되는 공고)를 저장하는 사용자. 코드 내 이미지형 판별 휴리스틱(`FieldExtractor.ts:210-242`)이 `[상세요강 이미지]` 섹션·짧은 SEO 텍스트+이미지 URL 패턴을 근거로 삼는 것으로 볼 때, 자체 채용페이지 없이 카드뉴스형 상세요강을 올리는 중소기업/스타트업 공고에서 이 문제가 자주 발생할 것으로 추정된다. 세그먼트 크기(전체 저장 공고 대비 비율)는 계측 공백으로 현재 미확인 — Open Questions 참고.

### 5. User Stories & Requirements

**P0 — Must Have**:

| # | User Story | Acceptance Criteria |
|---|---|---|
| P0-1 | 이미지형 공고 URL을 저장하면 자동으로 핵심 필드가 채워져 있으면 좋겠다 — 원본 이미지를 다시 열어 대조 타이핑하고 싶지 않다. | `is_image_based=true`인 공고 파싱 시 상세 이미지 OCR 텍스트가 `raw_text`에 병합되어 필드 추출기로 전달된다. 인식된 텍스트가 있으면 `qualifications`/`preferences`/`job_description` 중 최소 1개가 채워진 채 저장된다. OCR이 실패/타임아웃돼도 저장은 정상 완료된다(빈 필드로라도 저장). |
| P0-2 | 이미지형 공고도 다른 공고처럼 역량키워드로 필터링하고 싶다. | OCR로 `qualifications` 또는 `preferences`가 채워지면 키워드 추출기가 실행되고, 결과가 카드/필터 UI에 정상 노출된다. |
| P0-3 | (내부) 이 기능이 실제로 목표 지표를 달성했는지 측정할 수 있어야 한다. | 파싱 완료 시 `is_image_based`, OCR 시도 여부, OCR로 필드가 1개 이상 채워졌는지를 PostHog 이벤트로 기록한다. Phase 1 배포 전 필수 선행 작업. |

**P1 — Should Have**:

| # | User Story | Acceptance Criteria |
|---|---|---|
| P1-1 | 자동 인식이 놓친 내용이 있으면, 내가 직접 이미지를 첨부해 보완하고 싶다. | `POST /jobs/:id/images` 업로드 성공 시 OCR이 실행되고 결과가 저장된다(OCR 실패해도 업로드 자체는 성공 처리). |
| P1-2 | 첨부한 이미지의 인식 결과가 이미 입력해 둔 내용과 다르면, 그냥 덮어써지지 않고 내가 먼저 확인할 수 있었으면 한다. | "이미지로 필드 채우기" 액션 호출 시 빈 필드는 즉시 채우고, 값이 있는 필드 중 OCR 결과와 다른 필드가 있으면 저장 전 "이미지 기반 내용으로 필드값을 덮어씌우겠습니까?" 확인 팝업을 띄운다. 사용자가 확인하면 해당 필드까지 덮어써 저장하고, 취소하면 기존 값이 그대로 유지된다. 인식된 텍스트가 전혀 없으면 명확한 에러(`400 no_ocr_text`)를 반환한다. |

**P2 — Nice to Have / Future**:

| # | User Story | Acceptance Criteria |
|---|---|---|
| P2-1 | 흐릿하거나 회전된 이미지도 인식이 잘 됐으면 한다. | Phase 1 실측 정확도가 목표(60%) 미달일 때, 이진화/회전 보정 등 전처리 착수. |
| P2-2 | 영문 등 비국문 공고 이미지도 인식됐으면 한다. | 딱풀이 국문 외 공고를 지원 대상으로 확장할 때 재검토. |

### 6. Solution Overview

CLOVA OCR(네이버 클라우드 플랫폼, General) API를 호출하는 OCR 서비스를 신설하고, 원격 이미지(파서가 자동 수집)와 사용자 업로드 이미지가 동일 API 클라이언트를 공유한다. 한글 문서 특화 엔진이라 국문 채용공고 인식률이 높고, 외부 API 호출이라 서버 CPU/워커 풀/언어팩 캐싱 부담이 없다(엔진 비교 테스트로 사전 검증됨). 파서가 이미 수집 중인 상세 이미지 URL 목록을 `ParsedFields`에 노출하고, `parseAndCreateJob` 진입 직후 단일 훅 지점에서 OCR 텍스트를 `raw_text`에 병합한다 — 이후 단계(분류/LLM 필드 추출/키워드 추출)는 기존 로직을 그대로 재사용하므로 변경 범위가 작다. OCR은 best-effort로 동작해 일부 이미지 실패·시간 예산 초과 시에도 지금까지 인식된 텍스트만으로 계속 진행하며, 저장 자체를 막지 않는다. 상세 설계(주입 지점, API, 워커 풀 크기, 환경변수, 에러 처리)는 `docs/ocr-feature-spec.md`를 참고한다.

### 8. Timeline & Phasing

- **Phase 1 (P0)**: 원격 이미지 자동 OCR + 키워드 게이트 조건 변경 + 계측 추가(P0-3). 선행조건: 이미지 샘플 정확도 검증(Open Questions 2번). 배포 후 성공 지표 실측.
- **Phase 2 (P1)**: 사용자 업로드 이미지 OCR + "이미지로 필드 채우기". Phase 1 지표가 목표에 근접할 때 착수.
- **Phase 3 (P2, 조건부)**: 이미지 전처리/정확도 개선, 다국어 지원. Phase 1 지표가 목표에 크게 못 미칠 때만 범위에 편입.

구체적 착수일/완료일은 팀 리소스가 확인되지 않아 이번 초안에서는 지정하지 않는다(Open Questions 참고).
